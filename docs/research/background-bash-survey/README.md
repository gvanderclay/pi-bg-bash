# Structured output of background-shell tools: comparison and what pi-bg-bash should copy

**Status (October 2026).** The `bash` shape this report reviews shipped in v0.2.2 (#22). Item 6 was settled differently: the schema is declared only when Pi's bash has one, so a text-only result stays honest. The follow-ups (items 1–5) are parked until a codemode script needs to read or wait on a task. The `#` numbers refer to a 164-entry discovery list that was not kept; each entry is named here, and `src/` line numbers are as of the review.

**Question.** Of the tools in this survey that return structured output, which handle it best, and what, if anything, should pi-bg-bash copy?

**Short answer.** Keep the current `bash` shape: on every branch it fills what it declares, and it matches the two closest comparators (#16 `@ian-pascoe/pi-termctrl`, #3 `@pify/shell-background`) and the Codex-style tools (#71–#73), which also signal "still running" by an id being present and `exit_code` being absent. The gap is the follow-up half: `bash_output`, `bash_tasks` and `bash_kill` are text only, so after `bash({background:true})` a script can launch but cannot branch on state or exit code without parsing text, and it has no way to wait for completion (the completion arrives as a follow-up message a running script cannot receive). Copy, as one follow-up change: (a) one declared task schema for the three tools, (b) a bounded blocking `wait` on `bash_output`, (c) suppression of the completion message when a read or wait already delivered the end.

**Weighting** (from the session that asked for this, because the user's Pi runs codemode by default and a tool resolves to an object there only if it declares `outputSchema` and returns matching `structuredContent`). In order: (1) the declared type matches every return on every branch, with no text-only gap, no field that lies, no sentinel; a tool with no schema that returns text is honest, a tool whose schema promises fields it does not fill is the worst case. (2) A script can chain without parsing text: the launch id goes into status/read/kill, which return objects to branch on (state, exit code once known, new output, truncation). (3) Compatibility with Pi's bash fields. I also looked for what makes a wait-for-completion loop in a script reliable.

**Checked:** 2026-10-19 (UTC). Local repository `9737c9a` on branch `bash-structured-result`. Pi `@earendil-works/pi-coding-agent` 1.0.0 as installed in `node_modules/`. Items marked **verified** were re-read in the source named (npm tarballs from `npm pack <name>@<version>` in a fresh `mktemp -d`, removed afterwards; GitHub files through `gh api …?ref=<pinned commit>`); everything else comes from the chunk reports and is said so. Sources are the versions the survey pinned; their age is `unknown`.

## Ranking

Under the weighting above.

1. **#16 `@ian-pascoe/pi-termctrl` 0.8.2.** (1) It wraps Pi's own bash, keeps Pi's `outputSchema` properties, and makes `exit_code` optional ("Absent only when the command was moved to the background"); the promoted result is exactly `{output, truncated, wall_time_seconds, background: {id, log_path}}`, no invented exit code (`src/bash-replacement.ts:299–317,407–430,491`, **verified**). Every companion tool declares a schema and returns the matching object (`src/terminal-tools.ts:993,1052,1163,1330,1404` schemas; `:1222,1383,1432` payloads, **verified**). (2) It is the only one with a blocking wait that takes ids: `terminal_wait {ids?, wait_ms ≤ 300000}` returns `{reason: exited|timeout|message|aborted|nothing_running, exited[], running[]}`, with `exit_code` only on entries that exited (`terminal-tools.ts:258–320`, **verified**). (3) Pi-compatible. Weaknesses: each tool has its own shape instead of one shared one; `terminal_wait` returns `reason:"message"` on a queued user message, so a loop must handle a non-terminal return; a non-promoted background launch yields after a fixed 2 s (`bash-replacement.ts:30`).
2. **#74 `pi-unified-exec` 0.13.1.** (1) All five tools declare a schema and build their structured result with one projection (`src/script-result.ts:24–120`, `src/index.ts:1127,1189,1242,1309,1379`, **verified**). (2) The best chaining: `exec_command` returns `session_id`, and `write_stdin`/`kill_session` take `session_id`; every result has `status: "running"|"exited"`, `running`, `exit_code` (omitted, never null, while running), `signal`, `truncated`, `omitted_bytes`, `log_path`; waiting is a `yield_time_ms` on `write_stdin` with a `wait_status` field (`index.ts:6–7,296,479`; the `wait_status` value list is from chunk-4, not re-read). A kill of an unknown id returns the same shape with `found:false` (`script-result.ts:106–120`). (3) Not Pi's bash shape. Weaknesses: it never sets `isError`, so a failed kill or a non-zero exit looks like a success to the model (`rg isError src` finds only the completion coordinator and renderer, **verified**); `status` and `running` say the same thing twice.
3. **#39 `pi-wake-jobs` 0.1.6.** (1) `job_start`, `job_status` and `job_stop` share one `{jobs: JobView[]}` schema and one `report()` builder, so no branch can diverge (`jobs.ts:150–165,550–563`, **verified**). (2) `job_status {job_id, wait ≤ WAIT_MAX_S (300 s)}` blocks until the job ends; when the wait ends with the exit it calls `collect(job)` so the wake-up does not open a second turn for news already delivered (`jobs.ts:115,421–428,834–840`, **verified**). Fields: `state`, `exit_code`, `elapsed_sec`, `tail`, `log` always present. (3) Not Pi-compatible. Weaknesses: `exit_code` is `null` while running rather than absent, `state` is an unconstrained string (`"running, ok, fail, or stopped"` in a description), input is `job_id` while the result field is `id`, and an unknown id throws.

**4th, and the compatibility winner: #3 `@pify/shell-background` 0.5.1.** It is the only other bash replacement that says why it keeps Pi's shape ("every script that reads `result.exit_code` breaks the moment it is installed", `src/structured.ts:2–12`, **verified**), adds `status` and `job_id`, and returns failed or killed branches as `isError:true` **with** `structuredContent` (`extensions/shell-background.ts:425–452`, **verified**). It loses on weight 2: `shell_status` builds a structured payload but registers no `outputSchema` (the only `outputSchema:` in the file is on `bash`, `:500`, **verified**), so scripts get text from the tool they need most; list and `shell_kill` are text only. It is honest (weight 1) but it breaks chaining. Its `shell_status {id, wait 0–300}` is the other blocking wait and is the only one that also guards the wake-up the right way round: a finished read marks `delivered`, a running poll never does (`:555–558`).

Also seen: **#14 `@signalridge/pi-background` 1.6.0** has one shared schema for all six tools (`src/tools.ts:15–50,67–90`, **verified**) but no blocking wait (the only time parameter in `tools.ts` is the job's own `timeout_ms`; its description says "No sleep-and-poll", **verified**), so a script has to poll `background_list`. **#2 `@tian.zuo/pi-background-terminals` 0.6.0** has `terminal_wait` (`settled[]`, `running[]`, `alreadyReported[]`) and a log read with `settled` and `complete` flags (`index.ts:122–150,1262–1290`, **verified**) but `terminal_stop` is text only; its rule that `exit_code` appears only for a natural exit (`index.ts:290–305`, **verified**) is worth knowing.

Harnesses and MCP add little for Pi-style structured output. **#150 OpenCode** declares a real output schema (`packages/core/src/tool/plugin/shell.ts:63–75`, **verified**) but puts the "moved to the background" notice in `output` (`:96–101`), a sentinel-in-the-data-field, and sets `codemode:false` (`:195`). **#147 Claude Code** has typed `BashOutput`/`TaskStopOutput` (`sdk-tools.d.ts:3282–3350,3553`, `@anthropic-ai/claude-agent-sdk@0.3.303`, **verified**) with no exit-code field at all; whether the CLI declares them as a schema is `unknown`. **#158 Oh My Pi** and **#159 OpenClaw** return typed `details` next to text, not `structuredContent` (their own script bridges read `details`; chunk-7 claim, partly re-read: `packages/tui/src/tools/wait.ts:48–87`, `bash-tools.exec-run.ts:705–717`). **#148 Codex** does declare `output_schema` for `exec_command`: `unified_exec_output_schema()` at `codex-rs/core/src/tools/handlers/shell_spec.rs:191–223`, commit `89461ea` (**verified**; chunk-7 had this as `unknown`); it is where #71–#73 got their shape. MCP: **#124** `{job_id}` → `{status}` with no exit code anywhere, errors as text (`models.py:10–114`, `server.py:34–199`, **verified**); **#103/#118** report an unknown session as `state:"dead"` plus `error` (an invented state, `tools.go:185–211`, **verified**); **#95** has the best MCP state model (`CommandStatus` enum, `exitCode` omitted until known, `outputTruncated`, `elapsedMs`, `src/types.rs:260–341`, **verified**; the `server.rs` wiring was not re-read).

Notes:

- pi-bg-bash's promoted result drops Pi's `exit_code` because Pi reports the 0 that `exec` resolved with at promotion (`foreground.ts:367–368`). #16 and #3 reach the same place. The cost for scripts written against Pi's bash: they must check `task_id` before trusting `exit_code`, because `r.exit_code === 0` is now `false` for a command that is still running. The declared description says this; #16 and #3 have the same property.
- #2 reports `exit_code` only for `done`/`failed`, "where a forced kill reports platform-specific codes" (`index.ts:290–305`). pi-bg-bash's `killed` tasks have no exit code by construction (`registry.ts:426–429`), so the rule holds for free.

## Does the current `bash` schema lie anywhere?

Weight 1 asks this first, and the answer from reading `index.ts` and `foreground.ts` is no, with one dead branch to know about:

- Launch fills `output`, `truncated`, `wall_time_seconds`, `task_id`; `exit_code` and `full_output_path` are optional and left out (`index.ts:59–68,76–81`). The test pins it (`test/background.test.ts:51`).
- Promoted: Pi's own object, `output` sanitized, `exit_code` removed, `full_output_path` retargeted when present, `task_id` and wall time added (`foreground.ts:366–379`).
- Completed foreground: Pi's object with `exit_code`, `output` sanitized (`foreground.ts:342–349`). Non-zero exit: Pi returns `isError:true` with the data; abort/timeout/no-exit-code throw, as Pi's own tool does.
- The one text-only return under a declared schema is `if (sanitized === undefined) return { content, details: undefined }` (`foreground.ts:366`). Pi 1.0.0 always returns `structuredContent` (`dist/core/tools/bash.js:292–305`, **verified**), so it should not be reachable; if Pi ever returns none, that branch hands a script a string where the schema promises an object, which is the bug this branch fixed. Consider making it throw. Whether the package's declared Pi peer range includes a Pi without `outputSchema` is `unknown` (`index.ts:60` would throw at load on one, which is loud, not silent).

## What to copy, in priority order

Items 1–4 are one follow-up change and share one helper. None is needed for this branch to be correct.

1. **Declare one task schema for `bash_output`, `bash_tasks`, `bash_kill`, and return it. Follow-up.**
   - Behaviour: `bash_output` returns `{ task_id, state: "running"|"exited"|"killed"|"exit unknown", exit_code?: number, reason?: string, output: string, truncated: boolean, unread_bytes: number }`; `bash_tasks` returns `{ tasks: Task[] }`; `bash_kill` returns the same task fields plus `outcome` (the values `killTask` already yields: `killed | finished | gone | cleared | stuck | leftover-stuck`). `exit_code` only when `state` is `exited`; `reason` only when `killed`; text stays as `content`. The field names above are a sketch, not copied from one tool.
   - Evidence: shared projection in #74 (`script-result.ts:24–120`), one `Job` in every #14 tool (`tools.ts:19–50`), one `JobView` in #39 (`jobs.ts:550–563`), `exit_code` only for a natural exit in #2 (`index.ts:290–305`), kill outcomes as data in Oh My Pi's `CancelOutcome` (`wait.ts:82–87`, **verified**). Pi: "Tools without `outputSchema` are passed to scripts as their text content" (`docs/extensions.md:147`).
   - Fit: follow-up (the brief put these tools out of scope for this branch). Needs tests in `test/output.test.ts` and `test/background.test.ts`, README and CHANGELOG lines. Every branch must fill the schema, so build all three results from one function; #3 shows the trap of building the object and never declaring it.
   - Cost: low. The state is one enum already (`registry.ts:29,36,54–57`, `notify.ts:66–72`), the page is computed in `readOutput` (`output.ts:38–72`), and the unread byte count exists in the "More remaining" note (`output.ts:125`).
2. **Make "finished" decidable in one read. Follow-up, part of item 1.**
   - Behaviour: derive `state` from the marker the read just saw, as the text already does with `stateText(task, code)` (`output.ts:48,62`), not from the registry state that updates on the next poll tick; and report `unread_bytes` so a script treats the task as done only when `state !== "running"` and `unread_bytes === 0`. `bash_output` moves `task.readPosition` (`output.ts:57`), so each byte is returned once; a loop that breaks as soon as `state` is `exited` can still leave output unread when the page was capped.
   - Evidence: #2's log read has `settled` and `complete` (`index.ts:122–150`, **verified**); #74 has `omitted_bytes`/`truncated`; #16's terminal results have `settle_reason`.
   - Cost: nil beyond item 1. Without it, a polling loop races the poller.
3. **A bounded blocking wait. Follow-up.**
   - Behaviour: an optional `wait` (seconds, clamped, default 0) on `bash_output` that returns the item-1 object as soon as the task ends or the wait elapses; the object tells the script which (`state`). Not a new tool unless the model must not confuse reading with waiting.
   - Evidence: #39 `job_status wait` ≤ 300 s (`jobs.ts:115,834–840`), #3 `shell_status wait` 0–300 s with a 250 ms poll (`shell-background.ts:534–539`), #16 `terminal_wait` (`terminal-tools.ts:258–320`), #74 `yield_time_ms`. All four exist because a completion message cannot reach a running script; #3's description says so for headless runs (`shell-background.ts:468,514`).
   - Fit: follow-up. It touches the tool description in `index.ts:21–28` ("do not sleep or poll `bash_output` to wait for it"), which would need a sentence for scripts.
   - Cost: medium. A loop over `task.state` and the log marker at the existing `LOG_POLL_MS` (50 ms in `foreground.ts`), honouring the tool's abort signal; the cap must stay under the tool timeout.
4. **Do not send a completion message for news a script already holds. Follow-up, ship with item 3.**
   - Behaviour: when a `bash_output` read (or wait) observes the task finished and reaches the end of the log, set `task.notified` so `notifyOnce` does not queue a `followUp` that starts another turn. A read of a still-running task must not set it.
   - Evidence: #39 "the wake-up for this job would open a second turn for news the model already holds" (`jobs.ts:836–839`); #3 "A still-running poll must never do this" (`shell-background.ts:555–558`). pi-bg-bash today: `notified` is set only on kill (`bash_kill` passes `notify:false`, `index.ts:136`, so there is already a precedent for "the caller has the news, send no message") and session end (`registry.ts:148,384,400`) and read in `notifyOnce` (`registry.ts:513–516`); `bash_output` does not touch it.
   - Fit: follow-up; it changes behaviour (a reading agent no longer gets a completion turn), so it needs a test, a CHANGELOG line and a README line. Risk: a read that returns the final page without the model looking at it, which is unlikely; only suppress when the page reached the end of the log.
   - Cost: low.
5. **Return a still-stuck kill as `isError: true` with the structured task. Follow-up, optional.**
   - Behaviour: `stuck` and `leftover-stuck` outcomes (the process group survived SIGKILL) return the object with `isError:true`; other outcomes are normal. Unknown id keeps throwing.
   - Evidence: Pi: "To report a failure that still carries data, return the result with `isError: true` instead of throwing" (`docs/extensions.md:147`); #3 for kill timeouts (`shell-background.ts:425–441`), #2 for failed waits (`index.ts:1262–1290`), #73 for non-zero exits (`src/result.ts:76`). #74 is the counter-example (a failed kill as a success).
   - Fit: follow-up; it changes what the model sees today (a normal text result).
   - Cost: low.
6. **Make the dead text-only branch throw. This branch, optional.** `foreground.ts:366` returns no `structuredContent` while the tool declares one; it is unreachable on Pi 1.0.0 (above), but a silent wrong-type return is the failure mode this branch exists to remove. One line.
7. **Do not add `status` to the `bash` result.** #3, #2, #74 and #150 have it, but each can return a finished job from the same call (`done`, `completed`), so the field carries information. #16, #71–#73 and Codex (`shell_spec.rs:191–223`) use id presence, like `task_id`. A `status` here would add states that cannot occur (`task_id` with `status:"done"`). The brief's reasoning stands.
8. **Do not add a log path to the launch result, and do not rename `task_id` or the inputs `id`.** #16 (`background.log_path`), #74 (`log_path`) and #39 (`log`) return a path, but pi-bg-bash gzips the log to `.gz` when the task ends (`foreground.ts:297`) so the path goes stale, and with item 1 a script does not need it. A script chains `bash_output({ id: r.task_id })` with no text parsing; the names differ in #3, #39, #2 and Claude Code as well, and renaming a parameter breaks the "keep their names" rule in `AGENTS.md`.
9. **Expose the promotion reason and the `waitFor` outcome. Not recommended now.** Claude Code has `backgroundedByUser` and `timedOutAfterMs` (`sdk-tools.d.ts:3306–3318`); pi-bg-bash knows `by` and whether `waitFor` matched (`foreground.ts:255,273`) but prints them in text only, and the "never appeared" case is a text note (`foreground.ts:350–356`). A script cannot tell the cases apart. Add an optional field only when a script needs it.

## Does the evidence support keeping the current `bash` shape?

Yes. It fills every declared field on every reachable branch; it extends Pi's schema as #16 and #3 do; it has no sentinel (#150 puts prose in `output`; #103 invents `state:"dead"`); it keeps Pi's `full_output_path` meaning, retargeted to the live log when promoted (`foreground.ts:374`), as #3 does with its job log; and errors match Pi's own tool. The shortfall is the three text-only follow-up tools and the missing wait, which is where #74, #16, #39 and #3 do better.
