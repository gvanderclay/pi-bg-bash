# Preventing sleep-and-poll waits in coding agents

**Question.** How do other coding-agent harnesses stop models using `sleep` or polling loops to wait for background shell tasks, and what is the most effective fix for pi-bg-bash?

**Short answer.** Use the completion event pi-bg-bash already has, explicitly tell the model to **end its turn** when that is its only remaining dependency, and enforce the narrow mistake at the tool boundary rather than relying on another prohibition in the description. Claude Code really does reject leading bare sleeps of **25 seconds or more**, but its own issue tracker shows that this does not cure the model habit and can redirect it into background timers or unnecessary watchers. A bounded blocking wait is useful for synchronous/programmatic callers, but there is no controlled evidence here that adding one by itself reduces sleep calls; Codex demonstrates that a wait tool can itself become an expensive polling habit. These conclusions distinguish verified implementation from reports below. [C1–C8, O1–O4, P1]

**Checked:** 2026-10-19 UTC. Local pi-bg-bash base `86d276fa6d04890e1cd548af49ac0124ec16b9aa`; installed Claude Code **2.1.302**, npm Claude Code **2.1.303** declarations, Agent SDK **0.3.235** and **0.3.303**. GitHub source pins are in the source ledger. Most implementation sources are from the last month; older evidence is explicitly dated. No code was changed and no live model experiment was run.

## Start with what is already known locally

The existing [structured-output survey](background-bash-survey/README.md) already recommends a bounded `wait` on `bash_output` and suppressing a completion notification when the wait has delivered the final result. Its comparisons of termctrl, unified-exec, wake-jobs and pify are not repeated here. The [kendex comparison](kendex-pi-background-tasks/README.md) already covers auto-diverted monitoring loops and output wakes. This report concentrates on enforcement, actual model failures, and other harnesses.

[P1] pi-bg-bash currently has the event-driven primitive other tools request: `sendCompletion` uses `{deliverAs:"followUp", triggerTurn:true}`; the background launch result says `Its completion is reported automatically.` The description says `do not sleep or poll bash_output`, but neither the launch result nor that sentence explicitly says **end your turn now**. `bash_output` reads immediately and has no wait parameter. Foreground promotion deliberately excludes commands starting with `sleep`, so those commands can block longer than the ordinary 120-second promotion limit. Sources: [index.ts at the local base](https://github.com/gvanderclay/pi-bg-bash/blob/86d276fa6d04890e1cd548af49ac0124ec16b9aa/src/index.ts), [notify.ts](https://github.com/gvanderclay/pi-bg-bash/blob/86d276fa6d04890e1cd548af49ac0124ec16b9aa/src/notify.ts), [foreground.ts](https://github.com/gvanderclay/pi-bg-bash/blob/86d276fa6d04890e1cd548af49ac0124ec16b9aa/src/foreground.ts), especially `BACKGROUND_DESCRIPTION`, the launch return, `sendCompletion`, and `promotable`; the current README was also read. `git log --all --oneline --grep='sleep\|wait\|poll'` finds `61ffa81 Tell the model to wait on a blocking command in the background, not sleep and check (#2)` and `343f379 Add waitFor to foreground bash: return once the text appears (#11)`: this is not a new missing instruction.

## 1. Claude Code: actual rejection, exact threshold, and limitations

### Verified installed implementation, not just a prompt leak

[C1] The installed executable identifies itself as `2.1.302 (Claude Code)`. Its embedded JavaScript contains the following parser and threshold (minified names retained):

```js
var Cyr = 25;
function tcs(e) {
  let n = og(e);
  if (n.length === 0) return null;
  let r = n[0]?.trim() ?? "";
  let s = /^sleep\s+(\d+(?:\.\d*)?)\s*$/.exec(r);
  if (!s) return null;
  let h = parseFloat(s[1]);
  if (h < Cyr) return null;
  let y = n.slice(1).join(" ").trim();
  return y ? `sleep ${h} followed by: ${y}` : `standalone sleep ${h}`;
}
```

This is a **leading bare numeric `sleep` statement** detector, not a general ban on the sleep executable, not a sum of delays, and not restricted to sleep-only commands. Its check returns `{result:false, message:..., errorCode:10}` **before execution** when enabled, the call is foreground, background execution is not forbidden by remote constraints, no `shellWallCapMs` is set, background completion notices are enabled, and additional feature/session predicates pass. One predicate is the rollout flag `tengu_amber_sentinel`, default false in its flag lookup. The other predicate's meaning was not resolved. Thus **the code is present, but the block is not unconditional in every session**. [C1]

The exact Bash rejection template in that executable is:

> Blocked: ${b}. To wait for a condition, use Monitor with an until-loop (e.g. `until <check>; do sleep 2; done`). To wait for a command you started, use run_in_background: true. Do not chain shorter sleeps to work around this block.

For a bare call it becomes:

> Blocked: standalone sleep 25. To wait for a condition, use Monitor with an until-loop (e.g. `until <check>; do sleep 2; done`). To wait for a command you started, use run_in_background: true. Do not chain shorter sleeps to work around this block.

This is first-party distributed executable evidence at a pinned version/hash, **not a live permission-path test**. Variable names collide across embedded chunks; only the context surrounding the Bash check was used. The quoted excerpts are preserved here so the result does not depend on retaining temporary extraction files.

[C2] Independent first-hand observations agree with this exact threshold on **2.1.235**: `sleep 24 && cmd` runs; `sleep 25; cmd` is blocked; `cmd; sleep 300; cmd`, loops containing sleep, and `sleep 15; sleep 15; cmd` run; `run_in_background:true` bypasses the block. ### Background, output, Monitor, and “Wait” are different capabilities

[C3] `run_in_background` returns a task identifier and supports completion notifications. In the installed 2.1.302 Bash description, the notification-enabled wording includes:

> `run_in_background` runs the command detached: it keeps running across turns and re-invokes you when it exits.

and, in an applicable description branch:

> You will be notified when it exits — do not poll its output file while waiting.

These strings are conditional: a separate fallback says nothing notifies the model and instructs it to read the output file. Do not assume notification behavior is identical in all Claude modes. Evidence: the same [C1] executable extraction, search `function Zzt(`, `function Ukr(`, and `Nothing notifies you when the command finishes`.

[C4] Historical `BashOutputTool` and `AgentOutputTool` were replaced by unified `TaskOutputTool` in **2.0.64**. Agent SDK **0.3.235** still declares `TaskOutputInput {task_id:string, block:boolean, timeout:number}`, with descriptions `Whether to wait for completion` and `Max wait time in ms`. This is a real task-specific blocking wait, not a generic `sleep` timer. But TaskOutput was deprecated in **2.1.83** and removed in **2.1.277**; current guidance is `Read` on the background task's output file. The current SDK's setting description explicitly says the tool was removed. Sources: [pinned Claude changelog](https://github.com/anthropics/claude-code/blob/ef7bfdca55d906929fe6b782025b93758c325074/CHANGELOG.md), sections 2.0.64, 2.1.83, 2.1.277; [`sdk-tools.d.ts` at 0.3.235](https://unpkg.com/@anthropic-ai/claude-agent-sdk@0.3.235/sdk-tools.d.ts), `TaskOutputInput`; [`sdk.mjs` at 0.3.303](https://unpkg.com/@anthropic-ai/claude-agent-sdk@0.3.303/sdk.mjs), search `taskOutputMaxChars`. These historical versions predate the last month except the checked current package. **Important naming distinction:** today's TypeScript interface `BashOutput` is Bash's return value, not proof that the old model-facing BashOutput tool still exists.

[C5] Monitor is an **asynchronous event watch**, not a synchronous wait-for-task-output tool. Current declarations take `description`, `timeout_ms`, and either `command` (each stdout line an event; exit ends the watch) or `ws` (WebSocket text frames as events). The documented default deadline is 300,000 ms, capped at 1,800,000 ms. The changelog introduced Monitor in **2.1.98** and later changed watches to always have deadlines, with a 10-minute limit in single-prompt `-p` runs. Sources: [`sdk-tools.d.ts` 0.3.303](https://unpkg.com/@anthropic-ai/claude-agent-sdk@0.3.303/sdk-tools.d.ts), `MonitorInput`; [changelog](https://github.com/anthropics/claude-code/blob/ef7bfdca55d906929fe6b782025b93758c325074/CHANGELOG.md), search `Added Monitor tool` and `Changed Monitor watches to always have a deadline`. No generic built-in **Wait** tool was found in either checked SDK tool union; an undocumented/gated one remains **unknown**. `ScheduleWakeup` exists in current declarations, but schedules a `/loop` wake 60–3,600 seconds later; it is not a blocking task wait. [same declarations]

### Does the block actually fix behavior?

[C6] **No evidence that it fixes the habit globally.** A report on **2.1.266**, 2026-09-09, shows the model requesting `sleep 90; tail ...` immediately after a background launch promised completion notification; it was rejected. The issue quotes the description, launch result and refusal, and says this repeats frequently: [#93111](https://github.com/anthropics/claude-code/issues/93111), **older than one month**. This supports “the guard prevents execution” but contradicts “the words/guard prevent the model composing another bad call.”

[C7] Worse, a first-hand report on **2.1.236** describes **42 background sleep timers**, 19 notifications and repeated wakeups after the real work was done. Foreground sleep rejection did not prevent background sleep-as-wait: [#90930](https://github.com/anthropics/claude-code/issues/90930), 2026-08-31, **older than one month**. Another report quotes the block's suggested `until` loop leading to unbounded orphan watchers: [#90475](https://github.com/anthropics/claude-code/issues/90475), **2.1.251**, 2026-08-28, **older than one month**. These are observations from reporters, not established root-cause analyses. They are strong reasons not to copy the refusal's remedy verbatim.

[C8] There is more recent first-party acknowledgement: Claude's **2.1.300** changelog says **“Fixed Claude polling a background command's output file or sleeping while it runs.”** It gives no benchmark or implementation explanation. Installed **2.1.302** contains this more actionable instruction in an autonomous-style string:

> Execute autonomously and minimize interruptions. If the only work left is waiting for a background task or monitor you started, end your turn now: you will be notified when it finishes or fires. Do not poll, sleep, or re-read its output while you wait.

Sources: [changelog 2.1.300](https://github.com/anthropics/claude-code/blob/ef7bfdca55d906929fe6b782025b93758c325074/CHANGELOG.md#21300); [C1] binary, search `If the only work left is waiting for a background task`. This proves that wording is shipped, **not** that every session receives it or that it caused the changelog's fix.

### Exact opencode wording worth copying

[N1] The current source defines this constant for background completion guidance:

> You will be notified automatically when the command finishes. The notification will include the command's output. Unless the user explicitly asks otherwise, DO NOT poll for completion, even if you need the final result to continue. Repeatedly sleeping and reading or searching the output file is polling, not useful work. You may read the current output if it lets you do useful work now, but do not repeatedly check it while waiting for the command to finish. Keep working on anything that does not depend on the result. If you have nothing else to do, end your response; you will be resumed automatically when the command finishes.

This separates **useful output inspection** from **waiting**, closes the “but I need the final result” loophole, and names the action that replaces a sleep. Its existence is verified; comparative efficacy is **unknown**. [N1]

## 3. Does a blocking wait outperform instructions alone?

**Unknown as a comparative behavioral claim.** No controlled experiment, published sleep-call rate, or before/after model evaluation was found in the checked sources. There is useful but weaker evidence:

1. **Availability alone does not solve it.** Codex already has `write_stdin` waits, yet [#13733](https://github.com/openai/codex/issues/13733), opened 2026-03-06 (**older than one month**), records repeated short empty polls, abandoning healthy long builds, and attempts to fix the wait window. A contributor explicitly [acknowledged an architectural gap](https://github.com/openai/codex/issues/13733#issuecomment-4331336018). This is direct user/contributor evidence, not an experiment. [O2]
2. **A stronger blocking primitive has anecdotal support.** One user [reported “extremely good results”](https://github.com/openai/codex/issues/13733#issuecomment-4019470036) from a shell shim plus MCP wait-until-completion tool after prompting had failed to keep the model waiting; they later marked the workaround impractical/outdated. Another author [published a tested wait-window patch](https://github.com/openai/codex/issues/13733#issuecomment-4395694449), pinning [commit c3956e3](https://github.com/SproutSeeds/codex/commit/c3956e3885d7c7bd7627b067032141fa82b95655). These support feasibility and a reported benefit, **not measured sleep reduction or an upstream fix**. [O3]
3. **Event-driven wakeup remains the stronger architectural target.** Codex's [#32188](https://github.com/openai/codex/issues/32188), 2026-07-10 (**older than one month**), asks for the exact lifecycle Pi already has: end turn, wait locally, wake once on exit, suppress duplicate wakes if output polling already observed completion. Treat this as a proposal. The checked Codex async watcher emits execution-end events; that alone does not prove those events restart an idle model. [O4]
4. **Do not repeat the issue's maximal token-cost claims as fact.** A Codex contributor [clarified the WebSocket transport sends deltas, not full history](https://github.com/openai/codex/issues/13733#issuecomment-4483392890), then [clarified the usage statement concerned subscription plans](https://github.com/openai/codex/issues/13733#issuecomment-4483493979). Repeated model callbacks are real; “each poll retransmits the whole conversation” and particular cost multipliers are not universal facts. [O2]

A completion wait and an output wait also differ. Returning on **any new output** can turn chatty progress logs into repeated LLM turns; waiting for **exit** is the appropriate default when the only dependency is the final status. A readiness condition needs a pattern/substring wait (Pi already has foreground `waitFor`), not an exit wait for a server intended to stay alive. This is a design inference grounded in [O1], [N1], and [P1], not comparative experimental evidence.

## 5. Ranked recommendation for pi-bg-bash

This ranking is an engineering recommendation from the evidence, **not a demonstrated model-performance ranking**.

1. **Ship a narrow execution guard plus an actionable correction; cover background timers too.** When at least one managed task is still running, reject a clearly standalone sleep-only call used as a timer, whether foreground **or** `background:true`, before spawning it. Prefer a deliberately narrow recognizer over a general shell-policy parser; add a leading `sleep N; <read/status>` recognizer only if the actual offending transcripts require it and parsing is trustworthy. Do not ban `sleep` nested in test fixtures, rate limiting, retries or a user-requested timing experiment. An all-purpose sleep ban breaks legitimate work; Claude's foreground-only guard admits the background-timer feedback loop. [C1, C2, C7] Suggested Pi-specific refusal (new proposal, **not** a quote from another tool):

   > Not run: background task(s) bg-1, bg-2 are still running and will notify you automatically when they finish. A sleep or another background timer is not needed. Continue independent work; if all remaining work depends on these tasks, end your turn now. The completion message will start your next turn. Do not replace this wait with shorter sleeps or repeated bash_output/bash_tasks calls.

   Use the actual live ids, and do not recommend Monitor, an `until` loop, or relaunching the command: Pi already owns the dependency. A refusal prevents this invocation's delay deterministically; **whether it reduces subsequent bad attempts is unknown**. Do not auto-background the rejected timer or automatically spawn a watcher. Guard tests should pin no process launch and cover foreground/background, no-running-task behavior, and legitimate sleep-containing scripts.

2. **Make the replacement action explicit in the launch/promotion result and concise tool guidance.** Change `Its completion is reported automatically.` to something like: **“You will receive its exit status and final output automatically. Continue independent work. If this is all you are waiting for, end your turn now; the completion message will start your next turn. Do not sleep, start a timer, or repeatedly call bash_output/bash_tasks to wait.”** Apply to both explicit background launch and promotion, and distinguish one useful progress read from repeated waiting. This copies the important causal wording from opencode and Claude 2.1.302 rather than adding another standalone prohibition. [N1, C8, P1] Wording alone is not enforcement; Claude's #93111 is the counterexample. Keep legitimate user-requested progress checks possible.

3. **Add bounded `bash_output` blocking completion wait when synchronous callers need it, not as the normal model workflow.** An optional `wait`/`timeout` parameter (default nonblocking, bounded, abortable) is a good small extension to the existing tool for codemode/headless callers that cannot consume an idle-turn notification. Wait locally until exit or the bound; return structured state and unread output; do not force a new tool name. Suppress the future completion wake **only once the final state/result has actually been delivered**, not on a running poll.
